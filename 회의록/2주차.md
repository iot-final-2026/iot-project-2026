### 2. 초기 데이터베이스 설계

프로젝트의 주요 기능을 기준으로 다음 4개 테이블을 중심으로 초기 DB를 설계하였다.

- `USER`
- `PRODUCT`
- `PRODUCTION`
- `ALERT`

#### USER

- 작업자 및 관리자 계정 관리
- 로그인 및 권한(Role) 관리

#### PRODUCT

- OpenCV 기반 제품 분류 결과 저장
- 제품 종류, 신뢰도, 이미지 경로, 분류 시간 저장
- 작업자 정보를 연결하여 작업자별 생산 실적 관리

#### PRODUCTION

- 날짜별 목표 생산량 관리
- 초콜릿 및 사탕 생산량 관리
- 완료된 초콜릿 세트 수 관리
- 작업자별 생산 현황 관리

#### ALERT

- 센서, 컨베이어, 카메라, OpenCV 관련 오류 저장
- 오류 종류 및 내용 관리
- 오류 처리 여부 관리
- 제품과 연결하여 오류 발생 제품 확인

---

### 3. 초기 테이블 관계 검토

초기 관계는 다음과 같이 구성하였다.

```text
USER 1:N PRODUCT
USER 1:N PRODUCTION
PRODUCT 1:0..1 ALERT
```

그러나 다음과 같은 문제점이 확인되었다.

- 제품은 시스템이 자동으로 분류하므로 제품과 작업자를 직접 연결하는 구조가 적절하지 않음
- 제품이 없는 상황에서도 센서·카메라·컨베이어·DB 등의 오류가 발생할 수 있음
- 하나의 제품에서 여러 오류가 발생할 수 있으므로 `ALERT.product_id`에 UNIQUE 제약을 두는 것은 부적절함
- 날짜만으로 제품과 생산 작업을 연결하면 동일 날짜의 여러 작업을 구분하기 어려움
- 오류 발생 당시 생산 라인을 담당한 작업자를 정확하게 추적하기 어려움

---

### 4. 설계 방향

문제점을 해결하기 위해 생산 작업 단위인 **생산 세션(Session)**을 기준으로 DB 구조를 재설계하기로 하였다.

- 작업자별 생산 실적 조회가 가능하도록 설계
- 생산 작업 시작 및 종료 시각 관리
- 동일 날짜의 여러 생산 작업 구분
- 제품과 생산 작업 간 관계 관리
- 오류 발생 당시 담당 작업자 추적
- 데이터 중복을 최소화하는 방향으로 테이블 구성

### 2. 프로젝트 데이터 관리 기준

본 시스템은 컨베이어벨트에 투입된 초콜릿과 사탕을 적외선 센서와 카메라로 감지한 후 OpenCV를 이용하여 자동 분류한다.

분류된 제품의 생산량을 집계하고, 설정된 수량만큼 박스가 채워지면 박스를 배출한 후 LCD, LED, 부저를 통해 작업자에게 박스 교체 및 포장 알림을 제공한다.

#### 제품 관리 기준

- 초콜릿: **10개 = 1세트**
- 사탕: **1개 = 1세트(단품)**

### 3. 생산 세션 테이블 도입

작업자가 실제 생산 라인을 운영한 단위를 관리하기 위해 `PRODUCTION_SESSIONS` 테이블을 도입하기로 하였다.

```text
USERS
  1
  │
  N
PRODUCTION_SESSIONS
  1
  │
  N
PRODUCTS
```

#### 도입 목적

- 작업자별 생산 실적 관리
- 생산 작업 시작 및 종료 시각 관리
- 동일 날짜의 여러 생산 작업 구분
- 오류 발생 당시 생산 라인을 운영한 작업자 확인
- 제품이 어느 생산 작업에서 처리되었는지 추적

작업자 확인 경로:

```text
PRODUCTS
→ PRODUCTION_SESSIONS
→ USERS
```

오류 발생 당시 작업자 확인 경로:

```text
ALERTS
→ PRODUCTION_SESSIONS
→ USERS
```

---

### 4. ALERTS 테이블 검토

`ALERTS`는 특정 제품 오류뿐 아니라 생산 완료, 박스 적재 완료, 장비 오류, 소프트웨어 오류 등 시스템에서 발생하는 다양한 알림을 통합 관리하도록 설계하였다.

#### 알림 예시

- 적외선 센서 응답 없음
- 카메라 촬영 실패
- OpenCV 제품 분류 실패
- 컨베이어 구동 실패
- 서보모터 박스 배출 실패
- 데이터베이스 연결 및 저장 실패
- 박스 가득 참
- 목표 생산량 완료

모든 알림이 특정 제품과 관련된 것은 아니므로 다음 FK는 NULL을 허용한다.

```text
session_id
component_id
product_id
```

#### 관계

```text
PRODUCTION_SESSIONS 1:0..N ALERTS
PRODUCTS            1:0..N ALERTS
SYSTEM_COMPONENTS   1:0..N ALERTS
```

하나의 제품에서 여러 오류가 발생할 수 있으므로 `ALERTS.product_id`에는 UNIQUE 제약을 적용하지 않는다.

---

### 5. SYSTEM_COMPONENTS 테이블 도입

센서와 장비뿐만 아니라 소프트웨어 및 DB 오류까지 통합 관리하기 위해 `SYSTEM_COMPONENTS` 테이블을 도입하였다.

#### 구성요소 예시

- 적외선 센서
- 분류 카메라
- 컨베이어 모터
- 분류용 서보모터
- 박스 배출 서보모터
- OpenCV 분류 모듈
- 관리자 웹 서버
- 생산 데이터베이스

#### 구성요소 종류

```text
SENSOR
CAMERA
CONVEYOR
MOTOR
SOFTWARE
DATABASE
```

### 6. PRODUCT_TYPES 테이블 도입

제품 종류와 세트 구성 기준을 관리하기 위해 `PRODUCT_TYPES` 테이블을 도입하였다.

| 제품 | 관리 단위 | 1세트 구성 수량 |
|---|---|---:|
| 초콜릿 | SET | 10 |
| 사탕 | SINGLE | 1 |

주요 컬럼:

```text
product_type_id
product_name
unit_type
set_quantity
is_active
created_at
```

관계:

```text
PRODUCT_TYPES 1:N PRODUCTS
```

### 7. 생산량 테이블 구조 검토

기존에는 생산 세션별·제품 종류별 생산량을 별도로 관리하기 위해 `PRODUCTION_COUNTS` 테이블을 구성하려고 하였다.

```text
PRODUCTION_COUNTS
- production_count_id
- session_id
- product_type_id
- target_quantity
- actual_quantity
- completed_set_count
```

검토 결과 다음과 같은 피드백을 반영하였다.

- `PRODUCTION_COUNTS`와 `ALERTS`의 직접 연결은 필요하지 않음
- `PRODUCTS`와 `ALERTS`의 연결은 필요함
- 현재 제품 종류가 초콜릿과 사탕으로 고정되어 있어 `product_type_id`를 이용한 별도 생산량 테이블의 필요성이 낮음
- 생산량 관련 컬럼을 `PRODUCTION_SESSIONS`에 통합할 수 있음

---

### 8. 최종 DB 구조 방향

구현 난이도를 줄이고 현재 프로젝트 범위에 맞게 관리하기 위해 `PRODUCTION_COUNTS` 테이블을 삭제하고 생산량 관련 컬럼을 `PRODUCTION_SESSIONS`에 통합하기로 결정하였다.

#### PRODUCTION_SESSIONS 주요 컬럼

```text
session_id PK
user_id FK
production_date
target_chocolate_set_count
target_candy_count
chocolate_count
chocolate_set_count
candy_count
status
started_at
ended_at
created_at
updated_at
```

#### 생산량 관리 기준

```text
초콜릿 완료 세트 수 = chocolate_count DIV 10
사탕 생산 실적 = candy_count
```

사탕은 단품 기준으로 관리하므로 별도의 `candy_set_count`는 두지 않는다.

### 9. 최종 테이블 구성

피드백 반영 후 총 6개 테이블로 설계하였다.

1. `USERS`
2. `PRODUCTION_SESSIONS`
3. `PRODUCT_TYPES`
4. `PRODUCTS`
5. `SYSTEM_COMPONENTS`
6. `ALERTS`

#### USERS

작업자와 관리자의 로그인 정보 및 권한을 관리한다.

```text
user_id PK
login_id UNIQUE
password
name
role
created_at
```

#### PRODUCTION_SESSIONS

작업자가 생산 라인을 운영한 작업 단위와 목표 및 실제 생산량을 관리한다.

```text
session_id PK
user_id FK
production_date
target_chocolate_set_count
target_candy_count
chocolate_count
chocolate_set_count
candy_count
status
started_at
ended_at
created_at
updated_at
```

#### PRODUCT_TYPES

분류 대상 제품의 이름, 관리 단위, 세트 구성 수량을 관리한다.

```text
product_type_id PK
product_name
unit_type
set_quantity
is_active
created_at
```

#### PRODUCTS

컨베이어에서 감지된 개별 제품의 이미지와 OpenCV 분류 결과를 저장한다.

```text
product_id PK
session_id FK
product_type_id FK NULL
confidence
image_path
classification_status
detected_at
```

분류에 실패한 경우 `product_type_id`는 NULL을 허용한다.

#### SYSTEM_COMPONENTS

센서, 카메라, 컨베이어, 모터, 소프트웨어, DB 등의 시스템 구성요소와 상태를 관리한다.

```text
component_id PK
component_name
component_type
status
description
updated_at
```

#### ALERTS

생산 완료, 박스 가득 참, 제품 분류 실패, 장비 및 시스템 오류를 저장한다.

```text
alert_id PK
session_id FK NULL
component_id FK NULL
product_id FK NULL
alert_type
result_status
severity
error_code
message
status
acknowledged_by_user_id FK NULL
created_at
acknowledged_at
```

`acknowledged_by_user_id`는 오류 발생 당시 담당 작업자가 아니라 **알림을 실제로 확인한 사용자**를 의미한다.

---

### 10. 최종 테이블 관계

```text
USERS 1 ───── 0..N PRODUCTION_SESSIONS

PRODUCTION_SESSIONS 1 ───── 0..N PRODUCTS
PRODUCT_TYPES       1 ───── 0..N PRODUCTS

PRODUCTION_SESSIONS 1 ───── 0..N ALERTS
PRODUCTS            1 ───── 0..N ALERTS
SYSTEM_COMPONENTS   1 ───── 0..N ALERTS

USERS               1 ───── 0..N ALERTS
                    (acknowledged_by_user_id 기준)
```

모든 테이블은 독립적인 PK를 가지며 부모 PK는 자식 테이블의 FK로만 사용한다. 따라서 모든 관계는 **Non-Identifying Relationship(비식별 관계, 점선)**으로 설계한다.

---

### 11. 최종 DB 설계 결정 사항

- `PRODUCTS.user_id`를 사용하지 않고 `session_id`를 통해 담당 작업자를 추적한다.
- `PRODUCTION_SESSIONS`를 작업자 및 생산 데이터의 기준 테이블로 사용한다.
- `PRODUCTS`와 `ALERTS`는 연결한다.
- `ALERTS.product_id`는 NULL을 허용하고 UNIQUE 제약은 적용하지 않는다.
- 제품과 관계없는 오류도 저장할 수 있도록 `ALERTS`를 `PRODUCTION_SESSIONS`, `SYSTEM_COMPONENTS`와 연결한다.
- `PRODUCTION_COUNTS` 테이블은 삭제한다.
- 생산량 관련 컬럼은 `PRODUCTION_SESSIONS`로 통합한다.
- 초콜릿은 10개를 1세트로 계산한다.
- 사탕은 단품 생산량으로 관리한다.
- 최종 ERD는 6개 테이블로 구성한다.

## 2026년 7월 22일

### 1. DB 설계 추가 검토

#### PRODUCTION_SESSIONS

`started_at`과 `created_at`의 역할을 구분하여 검토하였다.

- `started_at`: 실제 생산 세션을 시작한 시각
- `created_at`: 생산 세션 데이터가 DB에 처음 생성된 시각

관리자가 작업 계획을 미리 등록하는 기능을 구현할지 여부에 따라 두 컬럼을 모두 유지할 필요성을 추가 검토하기로 하였다.

#### ALERTS

알림에 연결되는 사용자 정보의 의미를 명확히 하기 위해 `user_id` 관계를 검토하였다.

- 오류 발생 당시 생산 작업자
- 알림을 실제로 확인한 작업자 또는 관리자

두 사용자의 역할이 다를 수 있으므로, 알림 확인 사용자는 `acknowledged_by_user_id`로 구분하여 관리하는 방향으로 정리하였다.

작업자가 생산 현장에서 생산 상태와 이상 상황을 빠르게 확인하고 컨베이어 라인을 제어할 수 있도록 구성한다.

#### 주요 기능

- 로그인
  - 작업자 번호 입력
- 안내문
- 작업 현황 및 진행도
  - 초콜릿 생산 현황
  - 사탕 생산 현황
- 라인 제어
  - 컨베이어 속도 조절
  - 시작 및 정지
- 알림 팝업
- 날짜 및 시간 표시
- 시스템 연결 상태 확인


### 4. 관리자용 화면 구성

### 2. 최종 DB 설계 방향

최종적으로 다음 6개 테이블을 기준으로 DB를 구성한다.

```text
USERS
PRODUCTION_SESSIONS
PRODUCT_TYPES
PRODUCTS
SYSTEM_COMPONENTS
ALERTS
```

각 테이블의 역할과 관계를 정리하고, ERD 및 실제 DB 구현을 위한 기준을 마련하였다.

## 2주차 종합 결정 사항

- 프로젝트의 실제 구현 범위를 **자동 분류 및 작업자 포장 알림 시스템**으로 명확히 수정하였다.
- 실제 밀봉·포장은 구현하지 않고, 박스 적재 완료 후 작업자에게 포장 필요 알림을 제공한다.
- 초기 4개 테이블 구조에서 검토를 거쳐 **6개 테이블 구조**로 DB를 확장하였다.
- 작업자와 제품을 직접 연결하지 않고 `PRODUCTION_SESSIONS`를 통해 생산 작업 단위로 관리한다.
- 생산량 관련 데이터는 `PRODUCTION_SESSIONS`에 통합한다.
- `PRODUCT_TYPES`를 통해 초콜릿과 사탕의 생산 단위 및 세트 구성 기준을 관리한다.
- `PRODUCTS`는 개별 제품의 이미지와 OpenCV 분류 결과를 저장한다.
- `ALERTS`는 제품 오류뿐 아니라 센서, 카메라, 컨베이어, 모터, 소프트웨어, DB 등의 오류와 생산 완료 알림을 통합 관리한다.
- 하나의 제품에서 여러 오류가 발생할 수 있으므로 `ALERTS.product_id`에는 UNIQUE 제약을 적용하지 않는다.
- 오류 발생 당시 생산 작업자는 `ALERTS → PRODUCTION_SESSIONS → USERS` 경로로 추적한다.
- 알림을 실제로 확인한 사용자는 `acknowledged_by_user_id`로 별도 관리한다.
- 모든 테이블 관계는 **Non-Identifying Relationship(비식별 관계, 점선)**으로 설계한다.
- 작업자용 화면은 **240 × 320 크기의 LCD 기반 HMI**를 기준으로 구성한다.
- 관리자용 화면은 **데스크톱 웹 기반 모니터링 시스템**으로 구성한다.
- 작업자 화면은 생산 현장 운영과 라인 제어에 집중하고, 관리자 화면은 생산 관리 및 시스템 모니터링에 집중한다.
- 7월 23일에는 최종 DB 설계서를 작성하여 이후 DB 구현 및 시스템 개발의 기준을 마련하였다.
